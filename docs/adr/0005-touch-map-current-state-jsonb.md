# Mapa de Toques is a replaced current-state fact, not a Snapshot-scoped history

ADR-0002 scoped Statistics under a Snapshot specifically so multiple captures could accumulate per Player-Season over time. Mapa de Toques (raw FotMob touch coordinates, aggregated into a percentage-per-grid-cell view) deliberately does not follow that pattern: each ingestion or backfill run overwrites the Player's previous Mapa de Toques outright, so only the latest Season's ever exists — same current-state treatment as `players.age`/`nationality`/`photo_url`, not `statistics`. This was a direct product call (only the current picture matters here; historical touch maps have no identified use), not an oversight — a future reader familiar with ADR-0002's Snapshot pattern would otherwise expect Mapa de Toques to accumulate the same way Statistics does.

Storage is a single `jsonb` column of raw `{x, y}` coordinates per Player (one row per Player, upserted), not one row per touch point. A single Player-Season carries on the order of 1,000-3,000 touches; row-per-touch would have multiplied the database's total row count by roughly 60x over `statistics` for data that's only ever read back whole and re-aggregated into a grid in Python — never queried touch-by-touch in SQL. The looser JSONB shape does cost the ability to filter/aggregate touches at the SQL level, judged an acceptable trade since no such use case exists today.

Mapa de Toques still always comes from the same League/Season entry that produced the Player's currently-shown Statistics (see CONTEXT.md), so the two stay consistent for a Player whose Statistics themselves came from a fallback League (ADR-0004) — it just isn't kept as Snapshot history the way Statistics is.
